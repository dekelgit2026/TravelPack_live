# ADR-002: Use Haiku for the routing step, prompt v2
Status: Proposed · 2026-11-13 · Pack: travel · Follows ADR-001

## Context
ADR-001 puts rules in charge of classification and policy status, and an LLM in charge of wording. This ADR covers the model's routing-and-flags step: read one request, return a route (`package`, `coordinator`, `ask_employee`), policy flags and a short reply. The prompt layer is in `prompts/travel/` (`system_v1.md`, `system_v2.md`, `schema.json`, `cases.csv`).
- Volume: about 260 trips a month (ADR-001, cost.md). ASSUMPTION: one routing call per trip.
- Cost target: ADR-001 sets none (OPEN QUESTION). Latency: ASSUMPTION of options in minutes, so seconds per call is far inside it.
- Ship bar: at least 80% and zero critical failures (`prompts/travel/cases-notes.md`), on 11 cases. TS09 and TS13 are tested at the rules layer, not here.

All runs use Haiku (`claude-haiku-5-5`). Rows are copied from `results/travel/scoreboard.md`.

The first two rows used checks that were later corrected (all three failures were weak checks: TS07 and TS16 required `package` when the input had no dates, TS15 rejected the $200 policy threshold). They are not comparable with the last four. The baseline (no model) scores 0/11.

**No model comparison was run.** Only Haiku was scored. This ADR chooses between two prompt versions on one model.

## Decision
Use **Haiku with prompt v2** for the routing step. Status stays Proposed until the real-data checks below are done.

## Why
- Rule from class: the cheapest option that meets the bar wins. Haiku is the smallest model, and both versions met the bar with zero critical failures in both corrected rounds.
- v2 scored higher (100% vs 91%, in both rounds) and costs slightly less per case ($0.00012 vs $0.00014). That is about $0.03 a month for v2 and $0.04 for v1 at 260 trips (cost per case x volume), for this call only. The explanation and Slack calls in cost.md are separate.
- **The difference is not decisive.** It comes from one case, TS03 (Berlin tomorrow): v1 asked for a return date, v2 went ahead. This is the same missing-dates ambiguity as the failures above, and the input has no dates. It says nothing about policy safety: both versions pass TS08 and TS16, and both set the right flags. With 11 cases, one case is about 9 points.

## What we accept (consequences)
- When a request has no dates, the model sometimes asks and sometimes proceeds. In the real flow the form requires dates (station 1), and the coordinator reads `reason` at the human checkpoint.
- The model's main design job, explaining three live options, is not tested: the pack has no case for it.
- TS09 (watch list) and TS13 (passport data) are not tested here; the rules layer owns them.
- A critical failure (TS08 business class without VP approval, TS16 ignoring the policy) blocks release whatever the percentage.

## Fallback
- **Fallback model:** none tested. Sonnet has not been scored, so a stronger model is a one-config change plus a `--compare haiku sonnet --prompt v2` run.
- **Fallback prompt:** v1 on Haiku. It also met the bar (91%, no critical failures) and is one line in the run command.

## Revisit when
- A new Haiku or Sonnet version is released, or the price changes: re-run the scoreboard for v2.
- A re-run of v2 scores below 80% or has any critical failure.
- Real examples are added to `cases.csv` (hard and adversarial cases, the three-option explanation, Slack questions): re-run v1 and v2, because the current gap is within noise.
- Monthly volume passes 2,600 trips (10x today): re-check cost, and the cost-per-trip target once ADR-001 sets one.
- The form or Slack path changes how dates reach the model: re-check TS03, TS07, TS12 and TS16.
