# ADR-001: LLM workflow with tools, rules for every policy check
Status: Proposed · updated 2026-11-13 · Pack: travel

## Context
Harbor & Pine handles about 260 trips a month, about 80% simple returns. Today a request takes 2 business days and 3.4 emails. The spec (v1) asks for a form-triggered workflow that assembles a bookable package from live booking-tool data, with a coordinator and manager approving. The AI must never charge a company card, never touch passport data, and never send a watch-list trip anywhere but security. The one purchase it can start is an outside-tool booking that the employee confirms and pays for with their own card. Prices must be fetched live or labeled as unverified outside-tool options.

## Options considered
| Rung | Fits v1? | Why |
|---|---|---|
| 1. Rules | Partly | Policy checks (T1-T6, T9) and form-based simple/complex routing are stable arithmetic. Cannot write explanations or answer Slack questions |
| 2. Single LLM call | No | Needs live search and outside-source lookups |
| 3. RAG | No | Policy is about 3 pages and fits in the prompt. Becomes necessary if the policy exceeds ~20 pages or per-country rules multiply |
| 4. LLM workflow with tools | **Yes** | Fixed steps that read real systems |
| 5. Agent | No for v1 | Steps do not vary per simple case. One bounded exception: the browser assistant that books an outside option (see Decision) |
| 6. Multi-agent | No | No distinct specialties |

## Decision
Rung 4, mixed design. Rules decide classification (from form fields) and every policy and approval status. The LLM writes the option explanations, answers Slack status and SLA questions, and phrases the outside-source comparison. Code computes the outside-option threshold (15% or $300 cheaper than the best in-tool option).

Fixed sequence for a simple trip: form, rules classify, booking-tool search, outside-source search, rules check policy and threshold, LLM explains, package goes to coordinator and (if out of policy) manager at once.

Outside-option booking: the employee books, not the workflow and not the coordinator. The planner asks "Can I book this?" with the item and total. After the employee confirms, a browser assistant (Claude in the browser) completes that one booking in the employee's own logged-in tab, with their own card and private email. No credentials, tokens or per-site MCP servers are stored, so sites without an MCP (Agoda, Skyscanner and similar) can be used next to Kiwi and Booking.com. The workflow stays rung 4; the assistant is a tool it hands a single booking to. It is the only agent-like step, and it is bounded: one booking, an allowlisted site, a per-booking confirmation, and a hard stop at login, MFA, CAPTCHA, a new-card form or a changed price.

## Why
- Outside sites differ page by page, which is the reason a browser assistant fits this step and a fixed API or MCP per site does not.
- Using the employee's own session avoids storing secrets and keeps the company out of the payment.
- Of 16 examples, 9 are simple returns the workflow can package; the other 7 route to a coordinator or security. This matches the card's ~80%.
- The model never decides policy status, so a wrong "in policy" cannot come from the model.
- Fixed steps make the guardrails enforceable: no booking tool call that charges, no profile data passed to the model.
- A lower rung cannot do the explanations or Slack; a higher rung adds unpredictable cost and behavior without a case that needs it.

## What we accept (consequences)
- The workflow handles only the steps we design. Anything unusual goes to a coordinator.
- Outside options cannot be booked in the booking tool. The employee pays up front with their own card; reimbursement and whether policy still applies are open questions in the spec.
- The assistant depends on the employee's own session and on each site's pages, so it can break when a site changes, and then the employee finishes on the site.
- The company has no control over the employee's personal accounts, so it keeps its own log of each assisted booking.
- Every trip still needs a coordinator click, even in-policy ones. Slower than full automation by design.

## Non-functional targets
| Requirement | Target | Source |
|---|---|---|
| Quality bar | At least 70% of simple trips with no coordinator change; zero critical failures in the test set (ship bar 14 of 16) | Spec §6, testset-notes |
| Latency | ASSUMPTION: options in 10 minutes | Spec §6 |
| Cost per task | OPEN QUESTION (not in the card) | Spec §6 |
| Volume | About 260 trips a month, about 210 simple; peak OPEN QUESTION | Card |
| Privacy & data | No passport, date of birth or loyalty data reaches the model; visa and passport checks return pass/fail only. Outside bookings use the employee's own browser session; nothing is stored. Privacy review of the assistant is an OPEN QUESTION | T7, spec §8 |
| Availability & audit | ASSUMPTION: business hours; log each approval and each outside-source label; log each assisted booking (site, item, total, confirmation) | T8 |
| Browser assistant safety | Zero bookings without the employee's confirmation; zero card, password or code entries by the assistant | Spec §3 |

## Revisit when
- The pilot criterion is met (70% of simple trips with no coordinator change): reconsider auto-approval and auto-booking, which needs a spec guardrail change first.
- More than 25% of simple trips need a second round of outside searching: consider an agent for that step.
- More than 25% of assisted outside bookings end with the employee taking over (login, MFA, price change): rethink the browser step.
- An outside site offers a booking API or MCP server: prefer it over the browser assistant for that site.
- The policy grows past ~20 pages or gains per-country rules: consider RAG.
